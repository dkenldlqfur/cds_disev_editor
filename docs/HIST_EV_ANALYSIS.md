## 2. LS12 아카이브 구조

`HIST_EV.CDS`는 `DISEV.CDS`와 같은 LS12 계열 압축 아카이브입니다.

| 파일 위치 | 구조 |
|---|---|
| `0x000` | 16바이트 식별 헤더, 원본은 `Ls12`와 공백 패딩 |
| `0x010` | 256바이트 압축 사전 |
| `0x110` | 파트 테이블 시작 |

파트 테이블 항목은 12바이트이며 세 값 모두 big-endian `u32`입니다.

```text
[압축 크기] [압축 해제 크기] [압축 payload 파일 오프셋]
```

압축 크기가 0인 항목에서 테이블이 끝납니다.

## 3. 압축 해제된 파트와 슬롯

파트 헤더:

```text
+0x00  내부 단계 번호 u16
+0x02  슬롯 수 u16
+0x04  슬롯별 오프셋 표
       [조건 상대 오프셋 u16] [본문 상대 오프셋 u16]
```

조건과 본문의 실제 위치는 `파트 시작 + 4 + 상대 오프셋`입니다.

각 슬롯은 조건과 본문 한 쌍입니다. 실행기는 슬롯을 앞에서부터 검사하며 조건이 참인 슬롯의 본문을 실행합니다. 거짓이면 다음 슬롯을 검사합니다. 연속 조건은 기본적으로 AND이고 `50`이 앞뒤 조건을 OR로 연결합니다.

편집기는 파트에 슬롯을 최소 1개 유지하고 최대 16개까지 저장합니다. 추가 슬롯은 빈 조건과 본문 종료만 가진 상태로 생성합니다.

## 4. 파일 종류 판별

파일명과 파트 수만으로 판별하면 사용자 수정 파일을 잘못 분류할 수 있습니다. 편집기는 다음 순서를 사용합니다.

1. `HIST_EV`에서만 관찰된 고유 조건·명령 패턴을 검색합니다.
2. 내부 패턴만으로 확정할 수 없으면 중앙 선택 팝업에서 사용자가 발견물 이벤트 또는 역사 이벤트를 지정합니다.

`DISEV.CDS`와 `HIST_EV.CDS`는 같은 EXE 조건 인터프리터를 사용합니다. 따라서 전역 게임 상태만 읽는 공통 조건은 두 형식 모두에서 사용할 수 있게 했습니다.

### 편집기 조건·명령 분류 기준

조건과 명령의 "원본 사용 여부"와 "다른 이벤트 파일에서 실행 가능 여부"는 같은 뜻이 아닙니다. 편집기는 다음 기준으로 둘을 분리합니다.

- 조건: 현재 지원하는 39종은 모두 전역 상태를 읽는 공통 EXE 조건입니다. 두 파일에서 모두 선택할 수 있게 유지하되, 파일별 작업 흐름에 맞춰 분류와 순서만 다르게 표시합니다.
- 발견물 이벤트 조건 순서: `실행·논리 → 발생 위치 → 소지품·힌트 → 인물·후원자 → 발견 진행 → 도시 상태 → 날짜 → 수치·확률 → 이동·함대`
- 역사 이벤트 조건 순서: `실행·논리 → 발생 시점 → 발견 진행 → 도시 상태 → 발생 위치 → 소지품·힌트 → 인물·후원자 → 수치·확률 → 이동·함대`
- 명령: 양쪽 원본에서 사용이 확인된 공통 명령, 각 파일 원본에서 확인된 명령, 원본에는 없지만 공통 처리기와 재인코딩을 별도 확인한 명령을 구분합니다.
- 발견물 이벤트 명령 목록에서는 HIST_EV 분석으로 추가된 역사 세계 상태 명령을 숨깁니다. 역사 이벤트 명령 목록은 HIST_EV 원본 명령, 양쪽 원본 공통 명령, HIST에서도 별도 검증한 공통 처리기 명령만 제공합니다.

설명 탭의 조건 경로는 `발견물 이벤트 | ...` 또는 `역사 이벤트 | ...`로 시작합니다. 각 조건 설명 끝에는 해당 원본 파일에서 실제 사용됐는지, 공통 처리기로만 제공되는지가 표시됩니다. 명령 경로는 `공통`, `발견물 이벤트`, `역사 이벤트`, `공통 처리기` 중 하나로 시작하며 설명에도 검증 범위를 함께 표시합니다.

## 5. 원본 HIST_EV 조건 분석

118개 슬롯의 조건 청크는 모두 현재 파서로 해석됩니다. 원본 파일에 실제로 등장하는 조건은 다음 8종입니다.

| 원본 형식 | 편집기 이름 | 횟수 | 실행 의미 |
|---|---|---:|---|
| `1C 17 [월] 16 [연도 u16]` | 특정 연·월 일치 | 100 | 현재 연도와 월이 모두 같을 때 실행 |
| `1B 17 [월] 16 [연도 u16]` | 기준 연도 이상 | 18 | EXE가 월을 읽고 버리므로 현재 연도가 기준 연도 이상일 때 실행 |
| `02 0B [발견물 u16]` | 발견 기록 있음 | 6 | 발견물의 두 진행 기록 중 하나 이상이 활성일 때 실행 |
| `28 08 [도시 u16]` | 도시 미등장·비활성 | 17 | 도시 레코드 `+0x04`의 `0x0004` 비트가 켜져 있을 때 실행 |
| `1B 0B [발견물] 16 [연수]` | 발견 후 경과 년수 (패치 필요) | 10 | 발견 연도−현재 연도를 `u16` 기준값과 비교하므로 양수 기준은 첫 연도 변경부터 참이 되어 N년을 구분하지 못함 |
| `28 00 [국가] 08 [도시]` | 도시 국적 불일치 | 2 | 도시 소속이 지정 국가와 다를 때 실행 |
| `27 08 [도시 u16]` | 도시 등장·활성 | 7 | 도시의 미등장·비활성 비트가 꺼져 있을 때 실행 |
| `27 00 [국가] 08 [도시]` | 도시 국적 일치 | 1 | 도시 소속이 지정 국가와 같을 때 실행 |

### 날짜 조건 주의점

`1B 17`의 월 바이트는 실행 결과에 영향을 주지 않습니다. 편집 화면에서는 연도만 입력받고 형식 보존을 위해 월을 `1`로 저장합니다.

반대로 `1C 17`은 연도와 월을 모두 정확히 비교합니다.

### 발견 후 경과 년수 패치 필요

`1B 0B`의 EXE 실행은 다음과 같습니다.

1. 발견물 ID로 발견 기록을 찾습니다. 기록이 없으면 비교용 연도 차이는 0입니다.
2. 기록이 있으면 대략 `발견 연도 - 현재 연도`를 계산합니다. 월 보정에도 별도 오류가 있습니다.
3. 결과와 저장된 기준 연수를 모두 `u16`으로 보고 `차이 >= 기준`을 검사합니다.

관련 위치는 1차 조건 처리 `0x407679`, 발견 기록 처리 `0x4076A1`, `u16` 비교 `0x4076FD`~`0x40770F`입니다. 마지막 비교는 signed 분기가 아니라 carry를 사용하는 unsigned 비교입니다.

기준이 양수 2일 때:

| 실제 경과 | 계산값(`u16`) | `계산값 >= 2` |
|---:|---:|---|
| 0년 | `0000` | 거짓 |
| 1년 | `FFFF` | 참 |
| 2년 | `FFFE` | 참 |
| 3년 | `FFFD` | 참 |

따라서 양수 N은 “N년 이상”이 아니라 발견 연도와 같은 해에는 거짓, 다음 연도부터는 N과 관계없이 참에 가깝게 동작합니다.

에디터에서 양수 2를 받아 원본에 음수 `-2 = FFFE`로 저장하는 것은 기술적으로 가능합니다. 그러나 unsigned 비교 때문에 동작은 다음처럼 됩니다.

| 실제 경과 | 계산값(`u16`) | `계산값 >= FFFE` |
|---:|---:|---|
| 0년 | `0000` | 거짓 |
| 1년 | `FFFF` | 참 |
| 2년 | `FFFE` | 참 |
| 3년 | `FFFD` | 거짓 |

즉 음수 저장은 “1년 후부터 N년까지”에 가까운 기간 조건이 되며, 원하는 “N년이 지난 뒤” 판정은 고치지 못합니다. 그 동작이 필요하면 EXE 비교 로직을 수정하거나 다른 조건 조합을 찾아야 합니다.

### EXE에는 있지만 원본 최상위 조건에 없는 예

- `3A 0B [발견물]`: 발견 기록 없음
- `5E 0B [발견물]`: 보고 완료 비트 `0x80`
- `1B 16 [연도]`: 기준 연도 이후·포함
- `1C 16 [연도]`: 현재 연도 일치
- `5D 17 [월]`: 현재 월 일치
- `36 16 [시작] 16 [종료]`: 연도 범위
- 위치, 소지품, 힌트, 인물·후원자, 상태값, 확률, 이동·함대 조건

이 조건들은 공통 인터프리터 구현이 확인됐으므로 편집기에서 두 파일 형식에 모두 제공합니다. “원본 HIST_EV에서 미사용”과 “실행 불가능”은 같은 뜻이 아닙니다.

## 6. 본문 명령 분석 현황

현재 원본 본문의 의미 있는 구간은 14,046바이트입니다. 편집기 파서는 `21 08` 복합 명령 180개를 모두 7바이트 한 행으로 묶습니다. 고정 국가형 66개와 도시 상태형 114개는 각각 이름이 붙은 편집 명령으로 표시합니다.

현재 원본 HIST_EV 본문에서 한 바이트 단위로 남는 미확인 표시는 없습니다. 마지막 7개 파트의 40바이트는 `26 00 [국가]` 형식 10개였으며, EXE 처리기와 국가 교체 흐름을 대조해 국가 생성 명령으로 확정했습니다. 파트 11·62의 `26 0E [힌트]` 2개는 힌트 등장·등록 명령으로, 10개 파트의 `19/1A 08 [도시] 1A [값]`은 도시 규모 증가·감소 명령으로 묶어 해석합니다. 기존에 `도시 필드 +0x40 설정 (미확인)`으로 표시한 798바이트는 도시 상태 설정 명령으로 확정됐습니다.

### DISEV·HIST_EV 공통 명령

### 역사 이벤트 전용·공통 처리기 명령 분류

HIST_EV 분석으로 추가됐고 발견물 이벤트 명령 목록에서는 숨기는 역사 이벤트 전용 명령은 다음 10종입니다.

- 문화권 소문 등록
- 도시 발견·개방
- 도시 점령지 해제
- 도시 시설 추가
- 도시 소속 국가 설정
- 도시 상태 설정
- 도시 규모 증가
- 도시 규모 감소
- 국가 생성
- 힌트 등장·등록

원본 HIST_EV에는 없지만 같은 EXE 처리기와 재인코딩을 확인해 역사 이벤트에서도 제공하는 `공통 처리기` 명령은 다음 6종입니다.

- 대사
- DSTILL 이미지 표시
- AVI 재생
- 이벤트 결과 코드
- 소지금 증가
- 델포이 신탁 출력

따라서 역사 이벤트 편집 목록은 `양쪽 원본 공통 6종 + 역사 이벤트 전용 10종 + 공통 처리기 검증 6종 = 22종`입니다. 발견물 이벤트 편집 목록은 전체 지원 명령에서 위 역사 이벤트 전용 10종을 뺀 81종입니다.

### `21 08` 도시 필드 설정군

1차 opcode `21`, 2차 대상 `08`은 도시 레코드를 선택합니다. 뒤의 피연산자 종류에 따라 변경 필드가 달라집니다.

| 형식 | 출현 | 분석 상태 |
|---|---:|---|
| `21 08 [도시] 00 [국가]` | 66 | **확정**: 도시 소속 국가 설정. 기존 국가의 수도를 바꾸면 같은 국가 소속 도시 전체를 새 국가로 이전 |
| `21 08 [도시] 18 [상태]` | 114 | **확정**: 도시 레코드 `+0x40`의 도시 상태를 설정 |
| `21 08 [도시] 19 [문화권]` | 0 | **확정**: 도시 레코드 `+0x58`의 문화권을 설정. 원본 HIST_EV에는 사용례가 없음 |

도시 상태 형식의 EXE 흐름:

- `0x409BAC`에서 상태값 `u16`을 읽고 `0x429D50`을 호출합니다.
- `0x429D50`은 값을 도시 런타임 레코드 `+0x40`에 기록하고, `0x429D60`은 같은 필드를 읽습니다.
- `0x429D70`은 읽은 값을 `0x53CE60`의 상태명 포인터 표에 인덱스로 사용합니다. 표의 0~13번 문자열은 `통상`, `전염병`, `기근`, `대기근`, `풍작`, `대풍작`, `대한파`, `혹서`, `노동력부족`, `전쟁`, `축제`, `호경기`, `불경기`, `대조선`입니다.
- 도시 초기화 `0x429AAB`~`0x429AB6`도 정적 도시 레코드 `+0x5C`의 기본 상태를 같은 setter에 전달합니다.
- 원본 HIST_EV의 114개 명령은 상태값 `0`, `1`, `9`, `13`만 사용합니다. 각각 통상 56회, 전염병 7회, 전쟁 46회, 대조선 5회이며 상태표 범위를 벗어난 값은 없습니다.

문화권 형식도 `0x409BC9`에서 `0x429D80`을 호출해 도시 레코드 `+0x58`을 씁니다. 문화권 소문 처리 `0x409A32`가 같은 `+0x58` 값을 지정 문화권과 비교하므로 문화권 설정으로 확정됩니다.

고정 국가 형식의 EXE 흐름:

- `0x409A57`: 1차 opcode `21` 처리
- `0x409A7E`: 2차 대상 `08` 처리
- `0x406C70` → `0x429970`: 도시 ID를 읽고 0x5C바이트 도시 런타임 레코드 반환
- 도시 레코드 `+0x00`: 현재 소속 국가 ID
- `0x429D40`: 현재 소속 국가의 런타임 레코드 참조
- `0x429D20`: 도시 레코드 주소로 도시 ID 계산
- 대상이 기존 국가의 수도이면 `0x409AE7`~`0x409B0A`에서 도시 226개를 순회하며 같은 소속을 모두 변경
- 수도가 아니면 `0x409B0C`에서 지정 도시 하나만 변경
- 표시 문맥이 있으면 `0x5387C0`의 `%s%s [%s]%s 공략했습니다` 형식으로 알림

이 명령은 기존의 `26 1C 1A 00 08 [도시]`, 즉 “도시를 주인공 국적으로 변경”과 다릅니다. `21 08 ... 00 ...`은 새 국가를 명시적으로 지정합니다.

### `26 00` 국가 생성

```text
26 00 [국가/세력 ID u16]
```

- 1차 opcode `26`은 최상위 점프 테이블 `0x40BEA4`의 0x26번 항목을 통해 `0x409EDF`로 이동합니다.
- 2차 대상 `00`은 하위 점프 테이블 `0x40C2D0`의 0번 항목을 통해 `0x409F03`으로 이동합니다.
- `0x409F03`~`0x409F1F`는 국가 ID를 읽고 `0x5859C0 + ID * 0x10` 국가 런타임 레코드의 `+0x04` 필드에 `1`을 기록합니다.
- 반대쪽 `22 00 [국가]` 처리기 `0x409D9B`~`0x409DB7`은 같은 필드에 `2`를 기록하며, 원본 역사 이벤트에서 국가 멸망 처리로 사용됩니다.

원본 HIST_EV의 `26 00`은 7개 파트에 10번 있습니다. 모노모타파·사파비·세이바니·히바·데마크·스웨덴·무갈·벵갈·퉁구 등 역사 이벤트로 새로 생성되는 국가에 상태 `1`을 기록한 직후, `21 08 ... 00 ...`으로 해당 국가의 영토를 배정합니다. 따라서 상태 `1`은 이 명령 문맥에서 **국가 생성·등장 상태**, 상태 `2`는 멸망 상태로 확정할 수 있습니다.

편집기는 이 형식을 `국가 생성` 한 행으로 표시하고 국가·세력을 이름 콤보박스에서 선택해 재인코딩합니다.

### `26 10` 도시 시설 추가

```text
26 10 [시설 비트 번호 u16] 08 [도시 ID u16]
```

- 1차 opcode `26` 처리기 `0x409EDF`가 2차 대상 `10`을 읽습니다.
- 하위 분기표는 `0x40A118` 처리기로 이동합니다.
- `0x40A118`~`0x40A157`은 시설 번호를 읽고, `08` 뒤의 도시 ID로 도시 런타임 레코드를 구합니다.
- 마지막 `or word ptr [도시 레코드 + 0x1C], 1 << 시설 번호`가 시설 비트를 켭니다.
- 반대 명령 `22 10 [시설] 08 [도시]`는 같은 비트를 AND로 끄므로 `도시 시설 제거`입니다.

원본 HIST_EV에는 시설 추가가 6번 있으며, 편집기는 도시와 시설을 각각 이름 콤보박스로 선택해 재인코딩합니다.

### `19/1A 08` 도시 규모 변경군

```text
19 08 [도시 ID u16] 1A [증가량 u32]
1A 08 [도시 ID u16] 1A [감소량 u32]
```

- 1차 opcode `19`와 `1A`는 `0x409352`의 공통 처리기를 사용하며 각각 연산 부호 `+1`, `-1`을 만듭니다.
- 2차 대상 `08`은 `0x409385`로 이동해 `0x406C70`으로 도시 ID의 런타임 레코드를 구합니다.
- 피연산자 종류 `1A`는 `0x406CE0`에서 뒤의 u32 상수를 읽습니다.
- 처리기는 `도시 레코드 +0x08 + (부호 × 값)`을 계산하고 `0x49E540`으로 결과를 `0~7` 범위에 제한한 뒤 다시 `+0x08`에 기록합니다.
- 도시 초기화 `0x4299A0`~`0x4299CB`은 정적 도시 레코드 `+0x28`을 런타임 도시 레코드 `+0x08`로 복사합니다. 정적 `+0x28`은 도시 규모이며, 규모값은 교역품 공급량과 함선 출시 가능 연도 계산에도 사용됩니다.

원본 HIST_EV에는 증가 3개, 감소 7개가 있으며 모두 변경량 1입니다. 편집기는 두 형식을 각각 `도시 규모 증가`와 `도시 규모 감소` 한 행으로 표시하고 도시 이름과 변경 단계를 편집합니다.

## 7. 이벤트 소문 시스템

`20 0A`는 대사를 즉시 표시하는 명령이 아니라 날짜가 붙은 이벤트 소문을 등록하는 명령입니다.

```text
20 0A [CP949 문자열] 00 08 [도시 u16]
20 0A [CP949 문자열] 00 19 [문화권 u16]
```

- 도시 대상은 지정 도시 한 곳에 등록합니다.
- 문화권 대상은 도시 ID `0`~`225`를 순회해 같은 문화권의 모든 도시에 각각 등록합니다.
- 소문 저장소는 파일별로 나뉘지 않은 전역 이벤트 소문 버퍼입니다.
- 레코드는 도시 ID, 문자열, 등록 날짜를 가집니다.
- 같은 문자열도 대상 도시마다 별도 레코드로 추가되며 자동 중복 제거하지 않습니다.
- 조회 시 현재 날짜 기준 최근 180일 이내 레코드만 후보가 됩니다.
- 도시의 소문 목록을 만들 때 이벤트 소문 분기가 약 50% 확률로 선택되고, 후보가 여러 개면 그중 하나를 다시 무작위 선택합니다.

관련 EXE 위치:

- `0x4099AE`: `20` 본문 처리기
- `0x4099F2`: 도시 대상 `08`
- `0x409A18`: 문화권 대상 `19`
- `0x44E1D0`: 소문 레코드 추가
- `0x44E3E0`: 도시·180일 조건으로 소문 조회
- `0x4A43F0`: 이벤트 소문 종류 및 후보 무작위 선택
- `0x4A3080`: 선택된 소문 문자열 반환

따라서 “1480년 2월이 되면 소문이 바로 화면에 뜬다”가 아니라, 해당 파트가 소문을 등록하고 이후 대상 도시의 소문·대화 목록을 생성할 때 후보로 사용되는 구조입니다.

## 8. 주요 파트 분석

### 파트 0 — 1480년 2월 기본 지역 소문

조건:

```text
1C 17 02 16 C8 05 FF
```

정확히 1480년 2월에 실행합니다. 문화권 소문 6개를 등록합니다.

- 이베리아: 아프리카, 이베리아 반도, 프랑스, 잉글랜드, 지중해 설명 5개

이베리아용 5개 중 하나가 즉시 표시되는 것이 아닙니다. 각 문화권 도시의 180일 이벤트 소문 후보에 들어갑니다.

### 파트 4 — 1484년 1월 몰다비아 멸망

조건:

```text
1C 17 01 16 CC 05 FF
```

정확히 1484년 1월에 실행합니다.

실제 본문 명령 경계:

| 행 | 원본 | 동작 |
|---:|---|---|
| 1 | `21 08 4D 00 00 25 00` | 몬카스트로(ID 77)의 소속을 오스만·투르크 제국(ID 37)으로 설정 |
| 2 | `22 10 02 00 08 4D 00` | 몬카스트로의 왕궁 시설 제거 |
| 3 | `23 08 4D 00` | 몬카스트로를 점령지로 설정 |
| 4 | `22 00 16 00` | 몰다비아 공국(ID 22)을 멸망 처리 |
| 5 | `20 0A ... 00 19 00 00` | 이베리아에 항복 소문 등록 |
| 6 | `20 0A ... 00 19 01 00` | 북유럽에 같은 소문 등록 |
| 7 | `20 0A ... 00 19 02 00` | 지중해에 같은 소문 등록 |
| 8 | `FF` | 본문 종료 |

소문:

> 드디어 몰다비아가 터키에게 항복했다는군. 발칸제국은 전부 사라센인의 손에 떨어진 셈이군.

기존 파서는 첫 행을 `21`, `08`, `4D`, `00` 등으로 잘못 나누며 `4D`를 실패 처리로 오인합니다. 여기서 `4D`는 독립 opcode가 아니라 도시 ID `0x004D = 77`의 하위 바이트입니다. 파트 4에는 실패 처리 명령이 없습니다.

추가 EXE 추적으로 파트 4의 본문은 미확인 명령 없이 모두 해석됩니다.

- `21 08 4D 00 00 25 00`은 `21 / 08 / 도시 004D / 00 / 국가 0025` 구조입니다. `0x409A57`의 `21` 처리기에서 도시 레코드를 구하고, `0x409AB6`의 국가 지정 분기가 도시 레코드 `+0x00` 소속 국가를 37로 변경합니다. 대상 도시가 기존 국가의 수도라면 같은 기존 국가 소속 도시 226개를 순회해 함께 이전합니다.
- 초기 도시 데이터에서 몬카스트로의 소속은 몰다비아(ID 22)이며, 몰다비아 소속 도시는 몬카스트로 하나뿐입니다. 따라서 수도 일괄 이전 분기가 실행되더라도 이 파트에서는 결과가 몬카스트로 한 도시의 오스만 소속 변경과 같습니다.
- `22 10 02 00 08 4D 00`은 `0x409DD1` 분기에서 몬카스트로 시설 마스크 `+0x1C`의 bit 2를 지웁니다. 시설 ID 2는 왕궁입니다.
- `23 08 4D 00`은 `0x409E18` 처리기에서 도시 플래그 `+0x04`에 `0x02`를 설정합니다. 반대 명령 `25 08`이 같은 비트를 해제하므로 점령지 설정으로 확정됩니다.
- `22 00 16 00`은 `0x409D9B` 분기에서 국가 ID 22의 16바이트 런타임 레코드 `+0x04`를 `2`로 설정합니다. HIST_EV 사용 문맥상 몰다비아 멸망 처리입니다.

초기 데이터 기준으로 명령 순서에 따른 변화는 `소속 22→37`, `왕궁 제거`, `도시 플래그 0x02 설정`, `국가 22 상태=2`입니다. 즉 먼저 영토를 오스만에 넘긴 뒤 도시를 점령지화하고 몰다비아 국가 레코드를 멸망 상태로 바꿉니다. 편집기는 첫 `21 08 ... 00 ...` 7바이트를 `도시 소속 국가 설정` 한 행으로 표시하고 도시·새 소속 국가를 각각 선택해 편집할 수 있습니다.

### 파트 11 — 레콩키스타 완료와 서회항로 힌트 등장

파트 11에는 날짜가 다른 슬롯 두 개가 있습니다.

슬롯 1 조건:

```text
1C 17 05 16 D3 05 FF
```

정확히 1491년 5월에 실행합니다.

1. 말라가(ID 9)의 도시 상태를 전쟁(ID 9)으로 설정합니다.
2. 그라나다(ID 10)의 도시 상태를 전쟁(ID 9)으로 설정합니다.
3. 세빌리아(ID 7)에 “우리 에스파니아는 무적이네. 그라나다 공략은 이제 시간 문제다.”라는 소문을 등록합니다.

슬롯 2 조건:

```text
1C 17 02 16 D4 05 FF
```

정확히 1492년 2월에 실행합니다.

슬롯 2 본문 명령 경계:

| 행 | 원본 | 동작 |
|---:|---|---|
| 1 | `21 08 0A 00 00 01 00` | 그라나다(ID 10)의 소속을 에스파니아(ID 1)로 설정 |
| 2 | `21 08 09 00 00 01 00` | 말라가(ID 9)의 소속을 에스파니아(ID 1)로 설정 |
| 3 | `22 00 02 00` | 그라나다 왕국(ID 2)을 멸망 처리 |
| 4 | `21 08 09 00 18 00 00` | 말라가의 도시 상태를 통상(ID 0)으로 복구 |
| 5 | `21 08 0A 00 18 00 00` | 그라나다의 도시 상태를 통상(ID 0)으로 복구 |
| 6~8 | `20 0A ... 00 19 00/01/02 00` | 이베리아·북유럽·지중해 문화권에 그라나다 함락 소문 등록 |
| 9 | `26 0E 01 00` | 서회항로 힌트(ID 1)를 미획득 상태로 등장·등록 |
| 10 | `FF` | 본문 종료 |

마지막 명령은 네 개의 한 바이트 데이터가 아니라 `26 / 0E / 힌트 ID u16` 구조의 4바이트 명령입니다.

- 1차 opcode `26`의 처리기는 `0x409EDF`, 2차 대상 `0E`의 처리기는 `0x40A0EC`입니다.
- `0x406CB0`이 힌트 ID를 읽고 `0x58B4E0 + ID * 8`의 힌트 런타임 레코드를 반환합니다.
- `0x40A0F8`은 해당 레코드 `+0x04`의 상태 플래그에 `0x08`을 OR 합니다.
- 힌트 활성·미활성 조건 `0F 0E` / `12 0E`는 같은 상태의 하위 2비트만 검사합니다. 따라서 `0x08`만 설정한 이 명령은 힌트를 즉시 획득하거나 활성 조건을 참으로 만들지 않습니다.
- 별도 명령 `05 0E [힌트]`는 하위 상태를 획득 상태로 바꾸므로 `26 0E`와 역할이 다릅니다.
- 세이브 데이터에서 `0x08`은 등록됐지만 아직 획득하지 않은 힌트 상태로 사용되고, 획득 시 bit 0 등이 추가됩니다.

원본 HIST_EV에서 `26 0E`는 두 번만 사용됩니다. 다른 사용례는 파트 62 슬롯 2의 `26 0E 64 00`이며, 1526년 모하치 전투로 헝가리가 멸망한 직후 `성스테판의 관` 힌트(ID 100)를 같은 방식으로 등록합니다. 두 사용 문맥과 EXE의 실제 비트 기록을 함께 보면, 이 명령은 역사적 사건 이후 관련 발견 힌트를 후보로 등장시키는 명령으로 판단할 수 있습니다. 다만 등장한 힌트가 어느 시설·후원자 선택 과정에서 노출되는지까지의 UI 소비 경로는 별도 추적 과제로 남습니다.
