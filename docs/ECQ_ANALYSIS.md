명령 경계가 확인되지 않은 값은 원본 바이트 그대로 보존하며, 문맥상 추정한 이야기 내용과 EXE로 확인한 동작을 구분한다.

- 최종 갱신: 2026-09-20
- 분석 대상: `CDS95K_Win_220518/ECQ.CDS`, `EDG.CDS`, `EEX.CDS`, `EHT.CDS`, `PCQ.CDS`, `PDG.CDS`, `PEX.CDS`, `PHT.CDS`
- 교차 검증 EXE: `CDS_95.EXE`

## 판정 등급

- **확정**: EXE 처리기 또는 원본 재해석으로 명령 경계와 기록 동작을 확인함
- **부분 확정**: 기록 위치는 확인했지만 게임상 반환값의 이름이 남아 있음
- **추정**: 대사·조건 문맥으로만 파악한 의뢰 진행 내용
- **미확인**: 명령 경계 또는 실행 의미가 확인되지 않음

EXE의 파일명 포인터 표 `0x552750`은 `PEX → PDG → PHT → PCQ → EEX → EDG → EHT → ECQ` 순서로 위 여덟 파일을 보유하고, 새 게임 선택 흐름의 코드 `0x45DCD0`이 선택 인덱스로 이 표를 읽어 파일을 넘긴다. 따라서 이것들은 독립 포맷이 아니라 **시작 인물/시나리오 선택에 따라 하나를 고르는 외부 퀘스트 데이터 세트**다.

대사와 왕실·도시 조건을 보면 `E*`는 에스파니아(세빌리아·에스파니아 왕), `P*`는 포르투갈(리스본·포르투갈 왕) 계열임이 강하게 뒷받침된다. 단, 뒤 두 글자(`CQ`·`DG`·`EX`·`HT`)가 어떤 시작 인물 또는 직업을 뜻하는지는 EXE의 선택 인덱스 산출식을 아직 끝까지 추적하지 않았으므로 **미확정**이다.

파트 헤더와 슬롯 구조는 공통이다.

```text
+0x00  내부 단계 번호 u16
+0x02  슬롯 수 u16
+0x04  슬롯별 [조건 상대 오프셋 u16, 본문 상대 오프셋 u16]
```

실행기는 앞 슬롯부터 조건을 검사하고, 참인 슬롯의 본문을 실행한다. 거짓인 슬롯은 다음 슬롯으로 넘어간다.

## 2. 확인된 퀘스트 반환 형식

| 원본 | 상태 | EXE 동작 |
|---|---|---|
| `58 [값]` | **부분 확정** | 값 1바이트를 읽어 이벤트 런타임 레코드 `+0x04`에 `1`, `+0x10`에 `값+1`, `+0x08`에 `2`를 기록하고 현재 해석을 종료한다. 원본 사용값 `00`~`04`는 잔여 단계 수 `1`~`5`로 사용된다. |
| `06` | **확정** | 같은 레코드 `+0x04`와 `+0x10`에 각각 `1`을 기록한다. 이후 바이트 해석은 계속하며, 원본에서는 뒤의 `4C`/`4D`/`FF`와 조합된다. |
| `04` | **확정** | 다음 바이트를 소비하지 않는다. 이벤트 런타임 레코드 `+0x04`에 `2`를 기록한다. 호출부는 이 값을 감지하면 `-1`로 반환하므로, 퀘스트 해석 중단 상태로 동작한다. |
| `4C` / `4D` / `4E` | **확정** | 각각 독립된 1바이트 결과 명령이다. 런타임 레코드 `+0x08`에 각각 `0`(종료 후 후속 처리)·`1`(종료)·`2`(미종료)를 기록한다. |

`58` 처리기는 `0x40BE5C`, `06` 처리기는 `0x408B2F`, `04` 처리기는 `0x4089EC`에서 확인했다. 일반 결과 코드 `4C`·`4D`·`4E` 처리기는 각각 `0x40BDD5`·`0x40BDF5`·`0x40BE15`이며, 런타임 레코드 `+0x08`에 0·1·2를 기록한다.

세 코드 모두 해당 본문 해석을 끝낸다. 다만 `2`의 “미종료”는 이후 바이트 해석을 계속한다는 뜻이 아니라, 이벤트의 논리적 완료 상태를 확정하지 않는다는 뜻이다. 호출 전 레코드 `+0x08`의 초기값은 이미 `2`이므로, `4E`는 그 기본값을 명시적으로 다시 쓴다. 퀘스트 경로에서 `0x4AB460`은 `+0x08 == 1`일 때만 반환값 `1`을 내보내며, `0`과 `2`는 모두 `0`으로 반환한다. 이어 `0x4AB5F0`의 호출부 `0x4A248C`는 이 반환값을 검사한다. `1`이면 `0x4A23FE`로 점프하여 다음 기본 처리 가상 호출(`vtable + 0x40`)을 건너뛰고, `0`이면 그 기본 처리로 진행한다. 따라서 `4D`는 퀘스트 이벤트가 현재 처리 순서를 소비했음을 알리는 제어 신호다. 이 신호는 아이템 미소지 안내와 보상 완료 양쪽에서 쓰이므로 성공·실패로 이름 붙일 수 없다. 퀘스트 호출부에서 `4C`와 `4E`는 모두 기본 처리로 진행하며, 다른 호출부가 0과 2를 어떻게 구분하는지는 아직 확인되지 않았다.

`58`의 `값+1`은 같은 의뢰 묶음에서 현재 단계가 진행될수록 감소한다. 예를 들어 ECQ의 3단계 묶음은 0단계에서 `58 02`(잔여 3), 1단계 거절에서 `58 01`(잔여 2), 마지막 처리에서 `58 00`(잔여 1)를 쓴다. 5단계 묶음도 `58 04` → `58 03` → `58 02`로 이어진다. 따라서 UI는 이를 **퀘스트 잔여 단계 반환값**으로 표시한다. 다만 관리기가 이 값을 어떤 필드명으로 부르는지와 각 잔여 단계에서 어떤 파트를 재선택하는지는 소비 호출부를 더 추적해야 한다.

## 3. 의뢰 흐름

아래 의뢰명은 원본에 저장된 공식 파트명이 아니라 대사·조건에서 읽은 설명용 이름이다. 파일명의 약어를 게임 내 공식 분류명으로 해석하지 않는다.

파트 헤더의 내부 단계 번호(`step`)는 의뢰 묶음마다 다시 0부터 시작한다. 같은 묶음 안에서 `0 → 1 → 2 …`로 이어지고, 단계 1에서 기한을 설정한 뒤 단계 2 이후에서 만료·완료를 검사한다. **단계별 이야기 흐름은 원본 조건·대사·기한 상태로 강하게 뒷받침되지만, 상위 의뢰 관리기가 step을 선택하는 호출부는 아직 추적 중**이다.

`EDG.CDS`는 바르셀로나 구리 납품, 세비야→팔레르모 터번 배달, 알렉산드리아산 면화 납품, 신대륙 식량 공급, 의복 조달, 스페인 왕의 로마 외교 등 별개의 계약형 의뢰 묶음으로 구성된다. 공통 반환 형식과 화물 수량 검사·화물 매각 형식은 ECQ와 공유하지만, 일부 본문 바이트열은 아직 명령 경계 또는 동작이 미확정이다.

시작 조건에 쓰인 상태값 17은 명성이다. 원본은 국가·도시·건물·문화권·후원자 계약 없음·함대 선박 보유·해상/육상 이동·도시 국적 일치·기준 연도 이후·상태값 이상·OR 조건을 사용한다.

### 3.1 공통 기한 처리

상태값 29는 `STORY 의뢰 남은 기한(일)`이다. `43 2D 1C 1D 00 1A 00 00 00 00 ...`은 값 0을 기준으로 기한이 남아 있는 경로로 분기한다. 각 의뢰의 설정값은 다음과 같다.

| 의뢰 | 설정 원본 | 기한 |
|---|---|---:|
| 에스톡 | `26 1C 1D 00 1A B7 00 00 00` | 183일 |
| 동광석 | `26 1C 1D 00 1A B7 00 00 00` | 183일 |
| 알제 공략 | `26 1C 1D 00 1A 5B 00 00 00` | 91일 |
| 안트베르펜 호송 | `26 1C 1D 00 1A 5B 00 00 00` | 91일 |
| 마녀재판 구출 | `26 1C 1D 00 1A 5B 00 00 00` | 91일 |

### 3.2 파트 묶음별 실행 경로

#### 에스톡 조달 — 파트 0~2

1. 파트 0은 1500년 이후와 명성 2000·함선 보유·후원자 계약 없음의 시작 조건을 둔다.
2. 파트 1은 세빌리아(도시 7) 조합 시설(건물 9)에서 의뢰를 제시한다. 수락 시 선금 10,000, 기한 183일, 에스톡 판매 지역 소문을 등록한다. 거절 경로는 `58 01`로 반환한다.
3. 파트 2는 같은 조합에서 기한을 먼저 검사한다. 만료면 선금 10,000을 회수하고 반환 코드 `58 00`으로 끝난다. 기한 내에는 아이템 41 소지 여부를 검사해 납품·보상으로 이어진다. 아이템 미소지 안내와 납품 보상 완료 경로는 모두 마지막에 `4D`를 써 반환값 1을 만들고, 퀘스트 스케줄러의 현재 기본 후속 처리를 건너뛴다. 따라서 이 `4D`는 실패 표시가 아니다.

#### 아우크스부르크 동광석 — 파트 3~5

1. 파트 3은 1500년 이후, 명성 4000·함선 보유·후원자 계약 없음으로 시작한다.
2. 파트 4는 카디스(도시 8) 교역 시설에서 동광석 50개 납품을 요청하고, 선금 5,000과 기한 183일을 설정한다.
3. 파트 5는 기한 만료를 먼저 처리한다. 기한 내 경로에는 `43 2C 08 34 00 15 2A 00 1A 32 00 00 00 50 00` 교역품 분기가 있으며 원산 도시 52·교역품 42·수량 50을 읽는다. 조건이 충족되면 아래의 **교역품 전량 매각**으로 이어져 동광석을 넘기고 보상을 지급한다.

### 3.3 파트 5 슬롯 2 — 교역품 전량 매각

원본 `5B 08 34 00 15 2A 00`은 **확정**된 7바이트 본문 명령이다.

| 바이트 | 의미 |
|---|---|
| `5B` | 교역품 정산 계열 명령 |
| `08` | 원산 도시와 교역품을 함께 지정하는 하위 형식 |
| `34 00` | 원산 도시 ID 52 (아우크스부르크) |
| `15` | 교역품 ID 지정자 |
| `2A 00` | 교역품 ID 42 (동광석) |

EXE 처리기 `0x40B3C8`의 `08` 분기는 화물 목록(최대 8칸)을 순회하여 원산 도시와 교역품이 모두 일치하는 화물 수량을 합산한다. 일치한 각 화물 레코드는 원산 도시·교역품을 `-1`, 수량을 `0`으로 다시 기록하므로 **조건 확인만 하는 명령이 아니라 해당 화물을 전량 제거**한다. 이어 현재 도시의 교역품 가격·거래 보정으로 정산액을 계산해 플레이어 소지금에 더하고, 금액 표시를 요청한다.

따라서 이 행은 “아우크스부르크산 동광석을 전부 팔았다”라는 뒤 대사와 일치한다. 수량 50은 앞의 `43 2C ... 50 00` 분기가 확인하며, `5B` 자체에는 수량 인수가 없다. 즉, 조건을 통과한 뒤 조건에 맞는 화물을 **현재 보유한 전량** 매각한다.

### 3.4 파트 5 슬롯 2 — 교역품 수량 분기

`43 2C 08 34 00 15 2A 00 1A 32 00 00 00 50 00`은 **확정**된 15바이트 조건 분기다.

1. `43`은 다음 조건의 결과가 거짓일 때 상대 이동을 적용하는 분기 래퍼다.
2. `2C`는 두 수치의 `미만` 비교다.
3. `08 34 00 15 2A 00`은 원산 도시 52·교역품 42에 일치하는 화물 수량을 합산해 첫 수치로 만든다.
4. `1A 32 00 00 00`은 비교 기준 50이다.
5. 마지막 `50 00`은 조건 해석이 끝난 위치에서 더하는 상대 이동이다.

EXE `0x406D30`의 `08` 수치식은 화물 8칸에서 원산 도시·교역품이 일치하는 수량을 합산한다. `0x40A2FA`의 `2C` 비교는 `보유 수량 < 50`일 때 참을 만든다. 이 원본의 `43` 래퍼는 **거짓일 때 이동**하므로, 수량이 50 이상이면 `+0x50`을 적용해 “아우크스부르크산의 동광석 50통…” 부족 안내와 결과 코드 `4D`를 건너뛴다. 목적지는 바로 다음 성공 대사이며, 이어서 `5B` 교역품 전량 매각을 실행한다.

## 4. 편집기 처리

- 파일명·파트 수·`58 [값]` 반환 형식으로 자동 판별하지 않는다. 이벤트 파일을 열 때마다 중앙 팝업에서 `퀘스트 이벤트`를 직접 선택한다.
- `58 [값]`, `06`, `04`, `4C`/`4D`/`4E`는 명령 경계와 재인코딩 형식이 확인됐으므로 편집한다. `04`와 `4D`는 별도 행으로 표시한다. `58`은 원본에서 사용된 `0`~`4` 범위만 입력하게 하며, 화면에서는 잔여 단계 1~5로 해석해 표시한다.
- 8개 원본에서 확인한 일반 대사, 선택, 상태값, 금전, 아이템, 전투, 분기 명령은 기존 공통 인코더로 편집한다.

- 파트 5 슬롯 2의 `43 2C 08 ...`은 `흐름 제어 | 교역품 | 보유 수량 이상이면 이동`으로 표시한다. 원산 도시·교역품·최소 수량·성공 목적 행을 편집하며, 저장 시 상대 이동값을 다시 계산한다.

### 4.1 전체 파일군 미확인 항목 검사 (2026-09-20)

8개 파일의 총 266개 슬롯을 재검사한 결과, **미확인 조건열은 0개**다. 즉 조건은 전부 현재 파서로 경계와 형식을 읽는다.

본문은 처음 검사에서 ECQ만 미확인 그룹이 없고 나머지 파일에는 86개 묶음이 남았다. EXE의 명령 경계와 처리기를 재추적해 `19`/`1A 12 ...` 계열 및 그 앞의 호환 흐름을 분리한 뒤, **8개 파일·266개 슬롯에서 미확인 본문 행은 0개**가 됐다.

| 원본 형식 | 판정 | EXE로 확인한 명령 경계·동작 |
|---|---|---|
| `19 12 [후원자 u16] 1C 1C 00 1A [u32]` | **확정** | 선택 후원자 레코드의 `+0x20`에 값을 더하고 결과를 `0`~`100`으로 제한한다. `1A`는 같은 형식으로 값을 뺀다. 대사 “친밀도가 내려갔다”가 뒤따르는 원본 사용례와 일치하므로 UI는 **후원자 친밀도 증감**으로 표시한다. |
| `38 12 [후원자 u16]` | **확정** | 후원자 레코드의 사용 가능 비트 15를 해제한다. `38`의 `0D` 하위 형식은 인물 조우 처리이고, `12` 하위 형식은 후원자 처리다. UI는 **후원자 사용 가능 해제**로 표시한다. |

`38 12 3C 00 00 0A ...`의 실제 경계는 `38 12 3C 00` → 일반 대사 `00 0A ...`다. `3C 00`은 후원자 ID 60의 little-endian 값이며, 그 뒤 `00 0A`는 대사 접두사다. 이 경계를 잘못 나누면서 뒤 대사까지 미확인 행으로 연쇄 표시됐었다.
